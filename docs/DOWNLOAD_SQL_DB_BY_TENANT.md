# SQL Database Backup — Implementation Plan

> **Implementation note (route shape):** All endpoints in this plan live under the standard `v1` prefix only — there is no `superadmin` URL segment. The controllers are placed in `app/Http/Controllers/Api/` (not `Api/Superadmin/`). Authorization is an inline `isSuperAdmin()` check inside each controller method (no `role:super-admin` middleware alias exists in this project). The frontend pages live at `/backup` and `/restore` (not `/superadmin/...`) and are gated client-side by `usePermissions().isSuperAdmin`.

## 1. Executive Summary

**Goal:** Provide a UI and Artisan commands for the superadmin to download SQL backups in **two modes**:

1. **Full Database Backup** — a complete `mysqldump` of the entire `inventory` database (all 81 tables, all tenants, all shared data). Used for disaster recovery, server migration, or full-system cloning.
2. **Per-Tenant Backup** — a scoped export that extracts one tenant's data (59 tables filtered by `tenant_id`) plus the relevant shared data (products, brands, categories filtered by `business_type_id`). Produces a `.sql` file that can be imported into a fresh Laravel instance as a standalone UIMS app.

The superadmin picks the mode from the UI before triggering a download. Both modes produce a self-contained `.sql` file with an embedded header comment that identifies which mode was used — this header is read by the [Restore plan](./RESTORE_SQL_DB_BY_TENANT.md) to auto-detect the file type on import.

**Current State:** Single database `inventory` — all tenants coexist via `tenant_id` FK on 59 tables. Central reference data (products, brands, categories) has no `tenant_id` and is scoped by `business_type_id`.

**Why this matters:**
- Full DB backup: server migration, disaster recovery, staging-from-production snapshots
- Per-tenant backup: clients can request their data for compliance or migration; superadmin can spin up a standalone instance per tenant on demand
- No architecture changes needed — works with the current single-DB setup
- The mode selector gives the superadmin full control over backup granularity

## 2. Backup Modes

### 2.1 Mode Comparison

| Aspect | Full Database Backup | Per-Tenant Backup |
|--------|---------------------|-------------------|
| **Scope** | All 81 tables, all tenants, all shared data | 59 tenant-scoped tables + shared data for one `business_type_id` |
| **Method** | `mysqldump` CLI (entire DB) | Custom `ExportService` (row-level `WHERE` filtering) |
| **File size** | Large (all tenants combined) | Small (one tenant's slice) |
| **Use case** | Disaster recovery, server migration, full clone | Client data request, standalone instance per tenant |
| **Artisan command** | `php artisan db:backup {--output=./exports}` | `php artisan tenant:export {tenant_id} {--output=./exports}` |
| **API endpoint** | `POST /api/v1/db/backup` | `POST /api/v1/tenants/{id}/export` |
| **UI trigger** | "Backup Full DB" button on backup page | "Download SQL" button per tenant row |
| **SQL header** | `-- UIMS Full Database Backup` | `-- UIMS Tenant Export (ID: {id})` |
| **Restore behavior** | Replaces entire database | Replaces / merges one tenant's data |

### 2.2 SQL Header Convention (for restore auto-detection)

Every exported `.sql` file begins with a structured header comment that the restore service parses to determine the backup mode:

**Full DB backup header:**
```sql
-- =============================================
-- UIMS Full Database Backup
-- Database: inventory
-- Total Tables: 81
-- Tenant Count: 5
-- Exported At: 2026-07-10 12:00:00 UTC
-- Generated By: UIMS Backup v1.0
-- =============================================
```

**Per-tenant backup header:**
```sql
-- =============================================
-- UIMS Tenant Export
-- Tenant: Howlader Electric (ID: 1)
-- Business Type: Electric & Electronics
-- Business Type ID: 2
-- Exported At: 2026-07-10 12:00:00 UTC
-- Generated By: UIMS Export v1.0
-- =============================================
```

The restore service reads the first N lines and matches against `UIMS Full Database Backup` or `UIMS Tenant Export` to auto-detect the mode. See the [Restore plan §3](./RESTORE_SQL_DB_BY_TENANT.md#3-backup-mode-detection-restore-side).

## 3. Data Classification for Export

### 3.1 Full Database Backup (No Filtering)

All 81 tables are exported in their entirety — no `WHERE` clauses, no tenant scoping. This is a straight `mysqldump` of the `inventory` database:

```bash
mysqldump --single-transaction --routines --triggers \
  -u {$user} -p{$pass} {$db} > {$output}
```

The full backup includes:
- All 59 tenant-scoped tables (all tenants, all rows)
- All shared/reference tables (`products`, `brands`, `categories`, `units`, `attributes`, etc.)
- All system tables (`migrations`, `personal_access_tokens`, `jobs`, `failed_jobs`, etc.)
- Schema (`CREATE TABLE`), data (`INSERT`), triggers, and stored routines

### 3.2 Per-Tenant Data (Exported with `WHERE tenant_id = {id}`)

These 59 tables belong to exactly one tenant and are fully exported:

**People:** `users`, `customers`, `suppliers`
**Inventory:** `warehouses`, `bins`, `stocks`, `stock_movements`, `stock_aging`, `stock_locations`, `batches`
**Orders:** `purchase_orders`, `purchase_returns`, `purchase_return_items`, `sales_orders`, `sales_order_items`, `sales_returns`, `sales_return_items`, `sales_return_payments`, `deliveries`, `delivery_items`
**POS:** `pos_orders`, `pos_order_items`, `pos_sessions`, `pos_registers`, `pos_refunds`, `pos_refund_items`, `pos_hold_orders`
**Finance:** `accounts`, `accounting_integrations`, `accounting_sync_logs`, `journal_entries`, `failed_journal_entries`, `expenses`, `fiscal_periods`, `tax_rates`, `tax_entries`, `payments`, `bank_accounts`, `account_reconciliations`
**Settings:** `tenant_settings`
**Logs:** `activity_logs`, `audit_logs`, `alerts`, `notifications`
**Other:** `prescriptions`, `prescription_items`, `properties`, `property_items`, `mobile_stock_takes`, `mobile_stock_take_items`, `ecommerce_integrations`, `ecommerce_sync_mappings`, `third_party_logistics`, `consignment_agreements`, `consignment_stock`, `drug_database`, `drug_interactions`, `pharmacy_compliance`, `assembly_orders`, `assembly_order_components`, `bill_of_materials`, `abc_categories`

### 3.3 Per-Tenant Shared Data (Exported by `business_type_id`)

These tables are in the central DB but are required for the tenant's instance to function:

| Table | Export Filter |
|-------|--------------|
| `products` | `WHERE business_type_id = {tenant's business_type_id}` |
| `product_variations` | Via `product_id` → `business_type_id` |
| `product_images` | Via `product_id` → `business_type_id` |
| `product_barcodes` | Via `product_id` → `business_type_id` |
| `product_variation_attributes` | Via `product_variation_id` |
| `brands` | `WHERE business_type_id = {tenant's business_type_id}` |
| `categories` | Via `category_business_type` pivot |
| `category_business_type` | `WHERE business_type_id = {tenant's business_type_id}` |
| `units` | All (global) |
| `attributes` | All (global) |
| `attribute_values` | All (global) |
| `business_types` | The single row for the tenant's business type |

**Full DB Backup Flow:**
1. Superadmin selects "Full Database Backup" mode on the backup page
2. System runs `mysqldump --single-transaction` on the entire `inventory` database
3. Prepends the `UIMS Full Database Backup` header comment
4. Streams the file to the browser for download or saves to disk

**Per-Tenant Backup Flow:**
1. Superadmin selects "Per-Tenant Backup" mode and picks a tenant from the list
2. System connects to the single production DB
3. Queries tenant-scoped rows with `WHERE tenant_id = {id}` for all 59 tables
4. Queries shared data filtered by `business_type_id`
5. Generates a single `.sql` file with the `UIMS Tenant Export` header
6. Returns the file for download or saves to disk

**Import Flow (standalone instance, per-tenant):**
1. Clone the main app repo
2. Create a fresh MySQL database
3. Run `mysql -u root -p new_database < tenant_export.sql`
4. Update `.env` with DB credentials
5. `php artisan serve` — fully independent instance

## 5. Artisan Commands

### 5.1 Full Database Backup: `db:backup`

```bash
php artisan db:backup {--output=./exports} {--compress}
```

**What it does:**
1. Runs `mysqldump --single-transaction --routines --triggers` on the entire `inventory` database
2. Prepends the `UIMS Full Database Backup` header comment with metadata
3. Optionally compresses with `gzip` if `--compress` is passed
4. Writes output to `{output}/inventory_full_{date}.sql` (or `.sql.gz`)
5. Prints a summary with total row count, table count, file size, and duration

### 5.2 Per-Tenant Export: `tenant:export`

```bash
php artisan tenant:export {tenant_id} {--format=sql} {--output=./exports}
```

**What it does:**
1. Validates the tenant exists
2. Fetches the tenant's `business_type_id` and name
3. Iterates all 59 tenant-scoped tables, runs `SELECT * WHERE tenant_id = {id}`
4. Iterates shared tables filtered by `business_type_id`
5. Generates `INSERT INTO` statements with proper ordering (respecting FK dependencies)
6. Prepends `CREATE TABLE IF NOT EXISTS` statements for portability
7. Prepends the `UIMS Tenant Export` header comment with tenant metadata
8. Writes output to `{output}/tenant_{id}_{date}.sql`
9. Prints a summary with row counts per table

### 5.3 Output Format

**Full DB backup:**
```
exports/
  inventory_full_2026-07-10.sql          # Single self-contained file
  inventory_full_2026-07-10.sql.gz       # With --compress
```

**Per-tenant backup (split):**
```
exports/
  tenant_1_2026-07-10/
    01_schema.sql              # CREATE TABLE statements
    02_tenant_data.sql         # Tenant-scoped rows (59 tables)
    03_shared_data.sql         # Related shared data (products, brands, etc.)
    04_users.sql               # Tenant users (with hashed passwords preserved)
    manifest.json              # Metadata
```

**Per-tenant backup (single file):**
```
exports/
  howlader_electric_2026-07-10.sql    # Single self-contained file
```

### Step 6: Create Frontend Service

**File:** `services/backupService.ts`

```typescript
import apiClient from '@/lib/api/axios';
import type { ApiResponse } from '@/types/api.types';

export type BackupMode = 'full' | 'tenant';

export interface BackupJobStatus {
  status: 'processing' | 'completed' | 'failed';
  progress: string;
  progress_percent: number;
}

class BackupService {
  /** POST /api/v1/db/backup (full DB) */
  async backupFullDatabase(options?: { compress?: boolean }): Promise<{ job_id: number }> {
    const response = await apiClient.post<ApiResponse<{ job_id: number }>>(
      '/api/v1/db/backup',
      { compress: options?.compress ?? false }
    );
    return response.data.data;
  }

  /** GET /api/v1/db/backup/{jobId}/status */
  async getFullBackupStatus(jobId: number): Promise<BackupJobStatus> {
    const response = await apiClient.get<ApiResponse<BackupJobStatus>>(
      `/api/v1/db/backup/${jobId}/status`
    );
    return response.data.data;
  }

  /** POST /api/v1/tenants/{tenantId}/export (per-tenant) */
  async exportTenant(tenantId: string): Promise<{ job_id: number }> {
    const response = await apiClient.post<ApiResponse<{ job_id: number }>>(
      `/api/v1/tenants/${tenantId}/export`
    );
    return response.data.data;
  }

  /** GET /api/v1/exports/{jobId}/status */
  async getTenantExportStatus(jobId: number): Promise<BackupJobStatus> {
    const response = await apiClient.get<ApiResponse<BackupJobStatus>>(
      `/api/v1/exports/${jobId}/status`
    );
    return response.data.data;
  }

  /** GET download endpoint → returns blob URL for browser download */
  async downloadBackup(jobId: number, mode: BackupMode): Promise<string> {
    const endpoint = mode === 'full'
      ? `/api/v1/db/backup/${jobId}/download`
      : `/api/v1/exports/${jobId}/download`;
    const response = await apiClient.get(endpoint, { responseType: 'blob' });
    return URL.createObjectURL(response.data);
  }
}

export const backupService = new BackupService();
export default backupService;
```

  `tenant_id` bigint unsigned NOT NULL,
  -- ... full column definitions ...
  PRIMARY KEY (`id`)

-- =============================================
-- DATA: Tenant-Scoped Tables (WHERE tenant_id = 1)

## 9. Handling Edge Cases

| Case | Solution |
|------|----------|
| Full DB backup is very large (>1 GB) | Queue the job; offer `--compress` (gzip); stream download in chunks |
| Per-tenant has 0 rows in a table | Skip the table or emit `-- No data for table X` comment |
| Large per-tenant datasets (>1 GB) | Queue the job; stream download in chunks |
| Password hashes in `users` | Export as-is (bcrypt hashes); no special handling needed |
| Auto-increment IDs | Preserve original IDs so FK references stay valid |
| Binary/BLOB columns | Use `HEX()` / `UNHEX()` or standard MySQL dump format |
| Tenant deletion requested | Export per-tenant first, then soft-delete or anonymize |
| User switches mode while job is running | Disable mode toggle while a backup job is in progress |
| Full DB backup includes system tables (`migrations`, `jobs`) | Include them — needed for the schema to be consistent on restore |
| Concurrent full + per-tenant backup | Both allowed; `backup_jobs` table tracks each independently |

## 10. Security Considerations

- **Authentication:** Both backup endpoints require `auth:sanctum` middleware
- **Authorization:** Inline super-admin check inside the controller method — there is no `role:super-admin` middleware alias in this project; only superadmins can backup
- **Authorization scope:** Superadmin can backup the full DB or any tenant (intentional)
- **Rate limiting:** Max 1 full DB backup per 30 minutes; max 1 per-tenant export per tenant per 5 minutes
- **File access:** Exported files stored in `storage/app/exports/` — not publicly accessible
- **Cleanup:** Old exports auto-deleted after 7 days (configurable)
- **Audit log:** Every backup (both modes) is logged in `backup_jobs` with `mode`, `tenant_id` (if applicable), `initiated_by`, `file_size`, `timestamp`
- **Full DB sensitivity:** Full backups contain ALL tenants' data — extra caution on file storage and access; consider encryption at rest for full DB backup files

## 12. Out of Scope

This plan does NOT cover:
- Full multi-database separation (separate DB per tenant in production)
- Real-time data replication between instances
- Cross-tenant data sharing after export
- Tenant self-service backup (only superadmin)
- Incremental/differential backups (only full snapshots, per-mode)
- Backup encryption (file-level encryption is a future enhancement)
- Automatic scheduled backups (only on-demand from UI or CLI)
